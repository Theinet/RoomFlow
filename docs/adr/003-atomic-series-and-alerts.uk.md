# ADR-003: атомарні серії бронювань і дедупліковані сповіщення

[English](003-atomic-series-and-alerts.md) · **Українська**

**Статус:** прийнято

## Контекст

Частково створена щотижнева серія вводить користувача в оману: одна її частина
може конфліктувати, тоді як інша вже потрапила до календаря. Сповіщення також
не мають повторюватися після кожного polling-запиту.

## Рішення

- API спочатку розраховує всі дати серії, а потім виконує вставки в одній
  SQLite-транзакції.
- Якщо будь-який trigger знаходить конфлікт, транзакція відкатується цілком і
  API повертає `409` без жодної нової події.
- Сповіщення зберігаються в таблиці з ключем `UNIQUE(booking_id, kind)`.
  Вони мають окремі типи `start` і `handoff`; кожен тип може бути створений
  лише один раз для конкретної броні.
- Перенесення або скасування бронювання очищає застарілі `handoff`-сповіщення
  у тій самій транзакції, що й зміну календаря.

## Наслідки

- Серія або існує повністю, або не існує взагалі.
- Немає дубльованих toast-сповіщень, але початок і передача кімнати можуть
  бути доставлені окремо.
- Потрібні інтеграційні тести і для відкату серії, і для обох типів alert.
